# 커밋

일주일 게임잼에 맞춰 절차를 간단히 유지한다. 사용자가 커밋을 명시적으로 요청한 경우에만 실행한다.

커밋 메시지는 `type: 요약` 형식으로 작성하고 스코프는 사용하지 않는다. 타입은 아래 표의 영문 키워드를 사용하고, 요약과 본문은 한글로 작성한다. 예: `feat: 플레이어 이동 추가`.

| 타입 | 용도 |
| --- | --- |
| `feat` | 새 게임 기능·콘텐츠 추가 |
| `fix` | 오류·회귀 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 자동 테스트·검증 코드 변경 |
| `docs` | 기획·프로젝트·Notion 문서 변경 |
| `chore` | 빌드·패키지·저장소·도구 설정 변경 |
| `perf` | 기능을 유지하는 성능 개선 |
| `art` | 아트 에셋·시각 리소스 추가·수정 |

1. `git status --short --branch`, `git diff`, `git diff --cached`, `git log -5 --oneline`으로 현재 브랜치, 변경 범위, 최근 커밋 맥락을 확인한다. 새 파일은 내용도 읽는다.
2. 요청과 관련된 변경만 대상으로 삼는다. 기존 staged 변경이 요청 범위와 다르면 임의로 해제하거나 포함하지 말고 범위를 확인한다. 변경이 없으면 커밋하지 않고 알린다.
3. 변경에 필요한 검증만 수행한다. Unity 코드 검증이 필요하면 프로젝트가 일치하는 Unity MCP 인스턴스에서 컴파일 오류와 관련 테스트를 확인한다. 문서만 바뀌었다면 내용과 diff를 확인한다. 검증할 수 없었던 항목은 명시한다.
4. 위 표에서 변경의 주목적에 맞는 타입을 고르고 요약은 한글로 짧은 한 줄로 적는다. 기존 히스토리가 영문이어도 한글 작성 규칙과 스코프 없는 형식을 우선한다. 커밋 전에 **현재 브랜치, 대상 파일, 메시지, 검증 결과**를 한국어로 간략히 보고한다. 이미 받은 커밋 요청에 대해 재승인을 요구하지 않는다.
5. 대상 경로를 명시해 `git add -- <경로>`로 스테이징하고 `git diff --cached`와 `git diff --cached --check`로 최종 내용을 확인한 뒤 커밋한다. 관련 Unity 에셋의 `.meta`도 함께 포함한다. 완료 후 커밋 해시와 변경 요약을 짧게 알린다.

별도 요청 없이 push, amend, reset을 실행하거나 커밋 훅을 우회하지 않는다.
